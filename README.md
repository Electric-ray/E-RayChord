# ErayChord (Guitar Accompaniment Generator)

MuseScore 4용 "코드 기반 기타 반주 자동 생성" 플러그인 프로젝트.
기획서(`ErayChord_기획.txt`), 기술 설계서(`ErayChord_기술.txt`), 개발순서(`개발순서.txt`)를
기반으로 하며, **개발순서 문서의 원칙에 따라 1단계(PoC 검증)부터 시작**한다.

> 절대 처음부터 반주 엔진을 만들지 않는다. 먼저 MuseScore 4.7 플러그인 API로
> "무엇이 가능한지"부터 확인한다.

## 2단계 최종 결과

15/15 코드 모두 정확한 위치에 triad로 입력 확인됨. 마디 경계를 살짝
벗어난 위치(타이로 인한 싱코페이션)에 붙은 코드 하나가 처음엔 계속
스킵됐는데, 원인은 다음과 같았다:

1. 그 트랙에는 목표 tick과 정확히 일치하는 ChordRest 경계가 원래 없었다
   (다른 트랙의 타이 때문에 그 위치에 세그먼트는 존재하지만, 이 트랙
   자체의 리듬 구조엔 그 지점이 없었음).
2. 이를 해결하려고 쉼표로 gap을 메우는 로직을 넣었는데, 처음엔
   `setDuration(num, den)`가 "온음표 기준 분수"라는 걸 착각해서
   온음표를 `(4,1)`로 지정하는 바람에(실제로는 온음표 4개 분량)
   오히려 더 크게 밀려나는 회귀가 있었다. `(1, den)` 형태로 바로잡아
   해결.
3. 추가로 `cursor.rewindToTick(tick)` (문서화된 정확한 위치 이동 메서드)과,
   `addNote(pitch, true)`로 화음을 쌓을 때 커서가 벗어나는 알려진 버그에
   대한 우회법(음 하나 넣을 때마다 같은 tick으로 재이동)도 반영함.

## 7단계: `stage7/Stage7_VoicingEditor.qml` (마지막 단계)

기획서 5절 원칙대로, 코드별 운지를 직접 입력/저장/불러오기하는 도구다.
6단계(패턴 편집기)와 달리 **악보에서 자동으로 읽어오지 않는다** — 같은
음이라도 여러 프렛 조합이 가능하기 때문에, 프렛 번호를 사용자가
직접 입력하는 방식이다.

### 사용법

1. **코드 이름**(예: C, Am, G7), **운지 이름**(예: Open, Barre, Jazz)을
   입력하고, **프렛** 칸에 낮은 E현부터 높은 e현까지 6개를 공백으로
   구분해 입력 (뮤트=-1, 개방현=0). 예: `-1 3 2 0 1 0`
2. **미리보기** → 프렛보드 그림과 실제 음(피치) 확인
3. **저장** → `ErayChord/data/voicings/user_voicings.json`에 저장됨.
   같은 코드에 여러 운지를 쌓을 수 있고, "기본 운지로 저장" 체크박스를
   켜면 그 코드의 다른 운지들의 기본 지정은 자동 해제되고 이번 것만
   기본이 된다
4. 아래 **코드 → 운지** 드롭다운에서 골라 **불러오기**(수정용)나
   **삭제**를 할 수 있다

### 한계

- 표준 튜닝(E2-A2-D3-G3-B3-E4) 고정
- 여기서 저장한 운지 라이브러리는 4~5단계의 내장 운지 라이브러리와
  아직 자동으로 연결되어 있지 않다 (수동으로 `data/voicings/` 파일을
  참고해서 4단계 코드에 반영하거나, 추후 통합 작업 필요)

## 6단계: `stage6/Stage6_PatternRecorder.qml`

지금까지는 "코드를 읽어서 반주를 쓰는" 방향이었다면, 이번엔 반대로
**사용자가 직접 입력한 리듬을 읽어서 패턴으로 저장**하는 도구다.
기획서/기술 설계서 원칙대로 "패턴은 코드 이름을 저장하지 않는다.
리듬 정보와 연주 방식만 저장한다." v0.4부터는 저장/불러오기가 실제
플러그인 폴더 안에서 이루어지고, 뮤트도 실제 x 노트헤드로 쓰인다.

### 사용법 (두 단계)

**1. 패턴 추출 / 저장 / 불러오기**
1. 빈 트랙(코드 이름 없이)에 1~2마디 정도 리듬을 직접 입력
   - 음표 한 개(단음) = **베이스** 슬롯
   - 화음(여러 음 동시에) = **코드** 슬롯
   - 음표머리를 x(크로스헤드)로 바꾼 음 = **뮤트** 슬롯
   - 쉼표 = **쉼표** 슬롯
2. 그 마디(들)를 선택하고 이름 입력 후 **"패턴 추출"** → 리듬만 기억됨
3. **"파일로 저장"** → `ErayChord/data/patterns/`에 JSON으로 저장되고,
   `_index.json`에 목록이 갱신됨
4. 언제든 **"저장된 패턴"** 드롭다운에서 골라 **"불러오기"**로 다시 불러올
   수 있음 (플러그인을 새로 실행해도 목록이 유지됨)

**2. 이 패턴 적용**
5. 악보에서 실제 코드가 붙어있는 다른 마디 범위를 선택
6. **"이 패턴으로 미리보기 생성"** → 방금 추출/불러온 패턴을 그 코드
   진행에 반복 적용해 미리보기
7. **"악보에 쓰기"** → 실제 입력. 뮤트 슬롯은 x 노트헤드 음표로 들어감.
   Ctrl+Z로 되돌리기 가능

### v0.96 (최종 확인됨: 액센트 실제 악보 반영 성공)

문자열 대입 대신 `SymId.articAccentAbove` enum 참조 방식으로 바꿔서
해결됨 (뮤트 때 성공했던 `NoteHeadGroup.HEAD_CROSS`와 같은 패턴).
이제 패턴 추출 → 저장/불러오기 → 다른 마디에 적용(코드/베이스/뮤트/
지속/액센트 전부) → 악보 쓰기까지 전 과정이 실제 악보로 검증 완료됨.

### v0.95 버그 수정 (액센트가 실제 악보에 반영 안 되던 문제)

액센트가 캔버스/미리보기엔 잘 나오는데 실제 "악보에 쓰기"에는
반영이 안 되는 문제가 있었다. 원인: articulation 기호를 지정하는
프로퍼티 이름을 `symbolId`로 잘못 썼다 (실제로는 `symbol`). 존재하지
않는 프로퍼티라 에러도 안 나고 조용히 아무 효과가 없었던 것. 올바른
프로퍼티 이름으로 수정.

### v0.94 개선 사항 (캔버스 버그 완전 해결 + 액센트 기능)

- **캔버스 잘림 버그 완전 해결**: Canvas를 감싸는 컨테이너를
  `ColumnLayout` 대신 명시적 `width`를 가진 `Column`으로 바꾸고,
  워밍업 그리기도 `Qt.callLater`로 한 번 더 감쌌다. Canvas의 폭
  바인딩이 확정되는 시점과 최초 페인트 시점이 어긋나는 문제였던
  것으로 보인다.
- **액센트(>) 토글 추가**: C/B/M/S 버튼 위에 독립적인 액센트 토글
  버튼을 추가했다. 베이스/코드/뮤트와 완전히 별개라 어떤 타입 위에도
  켤 수 있다 (코드에 액센트, 베이스에 액센트 등). 캔버스에는 작은
  노란 삼각형(▶)으로 표시되고, 실제 악보에 쓸 때는
  `articAccentAbove` accent articulation이 붙는다.

### v0.93 버그 수정 (캔버스 잘림, 근본 원인 대응)

사용자 제안대로, **캔버스가 생성되자마자(패턴이 아직 없는 빈 상태에서)
한 번 미리 그리도록**(`Component.onCompleted: requestPaint()`) 해서
"워밍업"시켰다. 캔버스가 태어나서 처음 그리는 그 순간 자체에 크기
확정 타이밍 문제가 있었던 것으로 보이며, 실제 패턴 데이터가 들어오기
전에 미리 한 번 그려두면 그 문제를 비켜갈 수 있다. 빈 상태에서도
기준선(가로선)을 먼저 그리도록 함께 수정.

### v0.92 버그 수정 (캔버스 잘림, 재시도)

v0.91의 `onWidthChanged` 대응으로도 안 잡혀서, `requestPaint()` 호출을
`Qt.callLater()`로 한 박자 늦췄다 — 현재 이벤트 루프가 다 끝나고
레이아웃/크기가 완전히 확정된 뒤에 그리도록 함.

### v0.91 버그 수정 (초기 로드시 캔버스가 잘려 보이던 문제)

패턴을 추출/불러온 직후엔 캔버스가 잘려서(원래 크기보다 좁게) 나오다가,
편집 버튼을 아무거나 하나 누르면 그제서야 정상적으로 다시 그려지는
문제가 있었다. 원인은 QML Canvas의 흔한 타이밍 버그: 패턴 길이가
바뀌면서 캔버스 `width`도 같이 바뀌는데, 그 크기 변경이 실제로 적용되기
*전에* 첫 그리기가 일어나서 옛날(더 좁은) 크기 기준으로 그려진 것.
`width`가 바뀔 때마다 다시 그리도록(`onWidthChanged: requestPaint()`)
한 줄 추가해서 해결.

### v0.9 개선 사항 (캔버스-버튼 정렬)

리듬 악보(캔버스)와 버튼 격자가 서로 다른 계산식으로 배치돼서 줄이
안 맞는 문제를 고쳤다. 이제 캔버스와 버튼 격자를 **하나의 스크롤
영역 안에, 완전히 같은 "칸 너비(slotWidth)" 기준으로** 그려서, 캔버스의
동그라미/X와 그 아래 C/B/M/S 버튼 열이 정확히 세로로 줄맞춰진다.
안내 라벨("패턴 편집 (0.25박 단위...)")은 필요 없어서 제거함.

### v0.8 개선 사항

- 칸마다 있던 4개 버튼(C/B/M/S)을 가로 나열 대신 **세로로 쌓아서**
  전체 너비를 줄임 (가로 스크롤 부담 완화)
- C/B/M 버튼 배경색을 캔버스 색과 맞춤 (코드=빨강, 베이스=파랑,
  뮤트=검정). S(지속)는 캔버스에 따로 그려지는 색이 없어 기본
  스타일 그대로 둠
- **"파일로 저장" 버튼을 패턴 편집기 바로 아래로 이동** (맨 아래
  버튼 줄에서 분리)
- **버그 수정**: 추출 이후 이름/카테고리만 바꾸고 재추출 없이
  저장하면, 파일은 새 이름으로 저장되는데 인덱스에는 예전 이름이
  그대로 남아 드롭다운에 같은 이름만 계속 보이던 문제. 저장 시점에
  입력창 값으로 항상 최신화하도록 수정.

### v0.7 개선 사항 (큰 개편: 0.25박 격자 편집기)

- **캔버스 표기**: 슬래시 대신 **채운 동그라미(●)**로 표시 (코드=선 위,
  베이스=선 아래). 뮤트는 계속 X로 표시하되 이제 코드 전체를 의미함.
- **격자 기반 편집**: 이벤트 목록을 직접 고치는 대신, **0.25박(16분음표)
  간격의 고정 격자**로 다룬다. 각 칸 아래에 **C(코드) / B(베이스) /
  M(뮤트) / S(지속)** 버튼 4개가 나란히 있고, 그 밑에 범례가 한 줄로
  설명해준다.
  - **S(지속)**: 새 음을 만들지 않고 바로 이전 칸을 그대로 이어서
    늘린다(서스테인). 이전 칸도 지속이었다면 자연히 그 이전 음까지
    계속 이어진다.
- **뮤트 = 코드 전체**: 이전엔 코드의 가장 낮은 현 음 하나만 뮤트
  표기였는데, 이제 **운지의 모든 음**이 뮤트(X 노트헤드)로 들어간다.

내부적으로 패턴 데이터는 "고정 격자(`patternGrid`, 0.25박 간격) ->
압축된 이벤트 목록(`editEvents`, sustain 칸을 병합해서 duration을
늘림)" 두 단계로 관리된다. 저장/적용은 계속 압축된 이벤트 목록
형식(JSON)을 사용하므로 예전에 저장한 패턴 파일과도 호환된다.

### v0.6 개선 사항 (화면에서 직접 패턴 수정)

캔버스 미리보기는 보기만 되고 수정은 안 된다는 지적을 반영해, 캔버스
바로 아래에 **이벤트별 편집 목록**을 추가했다. 각 줄에서:

- **▲코드 / ▼베이스 / X뮤트 / 쉼표** 버튼으로 그 슬롯의 타입을 바로 전환
  (코드=선 위, 베이스=선 아래로 이해하면 "올리다/내리다"에 대응)
- **길이(박)** 입력창으로 그 슬롯이 몇 박 동안 지속될지 직접 수정

이를 위해 패턴의 각 이벤트가 "다음 이벤트까지의 간격"으로 길이를
암묵적으로 추론하던 방식에서, **자기 자신의 길이(`durationBeats`)를
명시적으로 갖는 방식**으로 데이터 구조를 바꿨다 (편집 가능하려면
이렇게 분리하는 게 맞다). 수정하면 캔버스와 미리보기가 실시간으로
같이 갱신된다.

### v0.5 개선 사항

- **한글 파일명 지원**: 전에는 이름에 한글이 들어가면 전부 `_`로
  치환돼버렸다. 실제 파일시스템에서 문제되는 문자(`\/:*?"<>|`와
  공백)만 치환하도록 고쳐서 한글 이름 그대로 저장된다.
- **카테고리 2단계 분류**: "카테고리"(예: 고고, 컨트리) 밑에 여러
  "패턴 이름"(예: 고고1, 고고2)을 둘 수 있다. 저장 시 카테고리를
  같이 입력하고, 불러올 때는 카테고리 드롭다운을 먼저 고른 뒤 그
  안의 패턴을 고른다.
- **리듬 악보 미리보기(Canvas)**: 패턴을 추출하거나 불러오면 바로
  아래에 슬래시 표기 형태의 리듬이 그려진다 — 기준선 위 슬래시는
  코드, 기준선 아래 슬래시는 베이스, X 표시는 뮤트. (실제 오선
  채보는 아니고, 리듬 확인용 단순 시각화)

### v0.4 개선 사항

## 1단계 PoC 검증 결과 (실제 MuseScore 4.7에서 확인됨)

실제 악보로 PoC를 돌려서 확인된, 앞으로 엔진 구현 시 그대로 따라야 할 규칙들:

1. **`SELECTION_END`는 선택 영역 "다음"이 아니라 선택 영역 안의 마지막 위치를 가리킨다.**
   즉 시작/끝 마디 번호 모두 `cursor.measure.no + 1`로 동일하게 0-based -> 1-based
   변환을 해주면 된다. (Test1에서 이 변환을 안 해줘서 End Measure가 하나 작게
   나오는 버그가 있었고, 수정 후 정상 확인됨)
2. **코드(Harmony)를 읽을 때는 반드시 트랙(스태프)으로 필터링해야 한다.**
   보컬/기타 등 여러 스태프 위에 같은 코드를 중복으로 입력해둔 악보가 흔한데,
   이 경우 같은 위치(tick)에 트랙이 다른 Harmony가 여러 개 붙어있어 필터링
   없이 읽으면 코드가 중복으로 잡힌다. (Test2에서 확인, 수정 후 정상)
3. **코드 심볼을 읽을 때 `cursor.next()`가 아니라 `segment.next`로 순회해야 한다.**
   `cursor.next()`는 ChordRest(음표/쉼표) 기준으로만 이동해서, 타이로 이어진
   음 등으로 인해 특정 위치를 건너뛸 수 있다. Segment 자체의 `next`로 순회하면
   빠짐없이 검사된다.
4. **`Cursor.addNote()` / `addNote(pitch, true)`로 단일 음표와 화음 입력 모두 정상 동작.**
   (Test3, Test4 통과)
5. **기존 트랙(스태프)에 커서로 직접 음표를 써넣는 방식은 문제없이 동작.**
   (Test5 통과 — 새 트랙을 코드로 자동 생성하는 기능은 여전히 미검증/보류,
   기본 전략은 "사용자가 미리 만들어 둔 트랙에 쓰기"로 유지)
6. **`FileIO`로 고정 경로에 JSON 읽기/쓰기 왕복 정상 동작.** (Test6 통과)
7. **MU4 플러그인에서 `Qt.quit()`은 쓰면 안 된다.** 무반응이거나 MuseScore
   전체가 종료될 수 있다는 보고가 있다. 대신 `quit()`(Qt. 없이)을 쓴다.

## 1단계: PoC 실행 방법

`poc/` 폴더의 6개 `.qml` 파일 각각이 독립된 플러그인이다. 하나씩 개별적으로
설치해서 실행 결과를 콘솔로 확인해야 한다.

### 설치 방법 (MuseScore 4)

1. `poc/` 폴더 안의 `.qml` 파일들을 MuseScore 플러그인 폴더로 복사
   - Windows: `문서\MuseScore4\Plugins\`
   - macOS: `~/Documents/MuseScore4/Plugins/`
   - Linux: `~/MuseScore4/Plugins/`
2. MuseScore 실행 → 상단 메뉴 **Plugins > Manage plugins...** (또는 Home 탭의 Plugins)
3. 목록에서 `Test1_ReadSelection` 등 각 테스트를 체크(활성화)
4. Plugins 메뉴에서 실행하면 **결과 창이 바로 뜬다.** 그 창 안의 텍스트가 결과다.

### 결과는 어떻게 확인하나요? (별도 프로그램 필요 없음)

MuseScore 4에는 MuseScore 3의 "Plugin Creator" 같은 내장 콘솔이 없고,
`console.log` 출력이 터미널이나 로그 파일에도 잘 안 잡힌다는 보고가 많다.
그래서 이 PoC 플러그인들은 애초에 **콘솔에 의존하지 않고, 실행하면 뜨는
작은 창(다이얼로그) 안에 결과를 텍스트로 직접 보여주도록** 만들었다.

즉, Plugins 메뉴에서 Test1~6 중 하나를 클릭하면:
- 작은 창이 뜬다
- 그 안에 "Start Measure : 3" 같은 결과가 그대로 적혀 있다
- 다 봤으면 "닫기" 버튼을 누르면 된다

별도 콘솔 프로그램, 터미널, 로그 파일을 뒤질 필요가 전혀 없다.

### 각 테스트의 목적과 확인할 것

| 파일 | 목적 | 성공 기준 |
|---|---|---|
| `Test1_ReadSelection.qml` | 선택한 마디 범위 읽기 | 콘솔에 Start/End Measure, Track 번호가 정확히 출력 |
| `Test2_ReadChords.qml` | 선택 범위 안의 코드(Harmony) 심볼 읽기 | 악보에 입력된 코드명이 마디 번호와 함께 출력 |
| `Test3_AddNote.qml` | 음표 하나(C4, 4분음표) 입력 | 선택 위치에 실제로 음표 생성, Ctrl+Z로 취소 가능 |
| `Test4_AddChord.qml` | 화음(C-E-G) 동시 입력 | 세 음이 하나의 화음(같은 스템)으로 생성 |
| `Test5_ExistingGuitarTrack.qml` | 트랙 목록 확인 + 기존 트랙에 입력 | 파트 이름 목록 출력, 선택 트랙에 테스트 음표 입력 성공 |
| `Test6_JsonFileIO.qml` | JSON 파일 읽기/쓰기 왕복 확인 | 저장한 JSON과 다시 읽은 JSON이 일치 |

이 5~6개 테스트가 모두 통과하면(기술 설계서 표현을 빌리면)
**"이미 프로젝트의 50%는 성공"**이다.

## 조사 결과 — MuseScore 4.7 플러그인 API 관련 주의사항

기술 설계서 8절에서 요청한 사전 검증 항목과 관련해, 진행 전에 확인된 사항:

1. **QML import 버전**: MuseScore 4.x에서도 플러그인은 여전히
   `import MuseScore 3.0`을 사용한다 (`4.0`이 아님). 실수로 4.0을 쓰면
   플러그인 자체가 로드되지 않는 사례가 다수 보고되어 있다.
2. **`writeScore()` / `readScore()`**: MuseScore 4.x에서 더 이상 구현되어
   있지 않다는 보고가 있다. 다만 우리 플러그인은 파일 저장이 아니라
   **커서로 현재 열린 악보에 직접 음표를 써넣는 방식**이므로 큰 영향은 없을 것으로 예상.
3. **새 트랙/파트 생성**: 공식적으로 안정적인 지원 여부를 확인하지 못했다.
   따라서 **1차 목표는 "기존 Guitar 트랙에 입력"으로 잡고**, 새 트랙 자동 생성은
   PoC(Test5)에서 실제로 가능함이 확인될 경우에만 추가 지원 기능으로 넣는다.
   (기획서 3.2절 요구사항과 일치)
4. **FileIO**: 고정 경로에 대한 읽기/쓰기는 되는 것으로 보이나, 네이티브
   "파일 열기" 다이얼로그는 4.x 플러그인에서 지원되지 않는다는 보고가 있다.
   → Import/Export UI는 파일 다이얼로그 대신 **고정 경로 + 텍스트 붙여넣기**
   방식도 대안으로 고려한다.

이 내용은 실제 MuseScore 4.7에서 PoC를 실행해본 뒤 `poc/RESULTS.md` 같은
파일로 검증 결과를 남기는 것을 추천한다 (아래 "다음 할 일" 참고).

## 8단계: 통합 — 실제 동작하는 `plugin.qml`

1~7단계는 전부 `stageN/`, `poc/`, `mvp/` 밑에 있는 **독립 실행형 테스트
플러그인**이었다. `engine/*.js`는 그 사이 내내 스텁(throw만 하는 상태)이었고,
`plugin.qml`도 "아직 개발 중" 안내만 띄우는 껍데기였다. 8단계에서 이 둘을
실제로 채워 "코드 선택 → Generate" 한 번으로 끝나는 완성형 플러그인으로
합쳤다.

### 무엇을 했나

- **`engine/*.js` 실제 구현**
  - `SelectionReader.js` : 선택 마디/트랙 읽기 (poc/Test1, stage6 검증 로직)
  - `ChordReader.js` : 선택 범위의 Harmony 심볼 읽기 (poc/Test2, stage6 검증 로직)
  - `VoicingEngine.js` : 코드 이름 → 피치. 기본 제공 운지(`open_chords.json`)와
    7단계에서 저장한 사용자 운지(`user_voicings.json`)를 병합, 라이브러리에
    없는 코드는 3화음(triad)으로 폴백
  - `PatternEngine.js` : 기본 제공 패턴(`_builtin_index.json`)과 6단계에서
    저장한 사용자 패턴(`_index.json`)을 하나의 목록으로 병합
  - `NoteGenerator.js` : 패턴 × 코드 진행 → 실제 음표 이벤트 (stage6의
    `buildApplyEvents`/코드 경계 분할 로직 그대로)
  - `Writer.js` : 이벤트를 악보에 기록 (rest 채우기, 뮤트 노트헤드, 액센트
    아티큘레이션까지 stage6와 동일)
- **`plugin.qml`**: 위 엔진들을 `import "engine/....js" as ...`로 불러와
  패턴 선택 → 운지 우선순위 입력 → 읽기/미리보기 → 악보에 쓰기 흐름의
  실제 GUI로 완성 (menuPath: `Plugins.ErayChord`)
- **`ui/PatternEditor.qml`, `ui/VoicingEditor.qml`**: stage6/stage7을 그대로
  복사해 정식 메뉴 경로(`Plugins.ErayChord.Pattern Editor` /
  `Plugins.ErayChord.Voicing Editor`)로 배치. 로직은 그대로라 회귀 위험 없음.
  원본 `stage6/`, `stage7/` 파일은 이력 보존용으로 남겨둠.
- **기본 제공 라이브러리 확충**
  - 패턴: GoGo Basic(기존) + Calypso Basic, Country Basic 신규 추가
  - 운지: 기존 C/G/Am/F/Dm/G7/Em에 D/E/A open 코드 추가, 전부 `default: true` 표시

### 알고 하는 한계 (다음 확장 대상)

- 마디 길이를 4/4 고정으로 가정한다 (다른 박자표 미지원 — Waltz 등은 이 확장이 되어야 추가 가능)
- 코드 구성음을 순서대로 하나씩 뜯는 진짜 "Arpeggio" 주법은 아직 지원하지 않는다
  (현재 엔진은 슬롯마다 "화음 전체" 또는 "단음"만 표현 가능)
- 새 Guitar 트랙 자동 생성은 다루지 않는다 (기획서/기술설계서 원래 방침대로,
  사용자가 미리 선택해 둔 기존 트랙에만 쓴다)

### 8단계에서 가장 먼저 확인할 것 (실기 테스트 필요)

`engine/*.js`를 별도 파일로 분리하면서 `.pragma library` + `.import MuseScore 3.0`
구문으로 `Cursor`/`Element`/`SymId`/`NoteHeadGroup` 같은 MuseScore 전역 enum에
접근하도록 했다. 이 방식은 Qt QML 공식 문서에 있는 정상적인 패턴이지만, 이
환경에는 MuseScore 실행 파일이 없어 직접 실행해 확인하지는 못했다. 실제
MuseScore 4.7에 설치해서 제일 먼저 확인해야 하는 것:

1. `plugin.qml` 실행 시 import 오류 없이 창이 뜨는지
2. 패턴 콤보박스에 "GoGo Basic [기본]", "Calypso Basic [기본]", "Country Basic [기본]"이 보이는지
3. 코드가 붙은 마디 선택 → "읽기 + 미리보기" → 이벤트 목록이 제대로 나오는지
4. "악보에 쓰기"로 실제 음표/화음이 들어가는지 (6단계에서 이미 검증된 로직이라
   여기서 문제가 생긴다면 십중팔구 (1)의 import 방식 때문일 것)
5. 문제가 생기면 가장 빠른 대응은 `engine/*.js`의 함수 본문을 `plugin.qml`
   안으로 그대로 옮기는 것이다(6·7단계가 실제로 쓰는, 이미 검증된 단일 파일 구조).

### 8-1단계: mute/accent 미표시 버그 수정

**증상**: Pattern Editor(=stage6)로 적용하면 액센트가 정상 표시되는데,
메인 `plugin.qml`로 적용하면 뮤트(X머리 음표)도 액센트도 표시되지 않음.

**원인**: `engine/Writer.js`가 자기 파일 안에서
`.import MuseScore 3.0 as MS`로 `NoteHeadGroup`/`Element`/`SymId` enum을
직접 가져다 썼는데, 이 방식으로 별도 `.js` 파일에서 가져온 enum이 기대한
값으로 풀리지 않았던 것으로 보인다(로직 자체는 stage6와 동일했으므로
로직 문제가 아니라 "다른 파일에서 MuseScore enum에 접근하는 방식"의
문제). try/catch로 감싸놓은 부분이라 에러 없이 조용히 실패했다.

**수정**: `engine/*.js`에서 `.import MuseScore 3.0` 구문을 전부 제거했다.
대신 `Cursor.SELECTION_START/END`, `Element.ARTICULATION`,
`SymId.articAccentAbove`, `NoteHeadGroup.HEAD_CROSS`, `newElement` 값을
**`plugin.qml`(보통의 `import MuseScore 3.0`으로 확실히 접근 가능한 곳,
stage6와 동일한 방식)에서 만들어 파라미터로 주입**하도록 바꿨다.
`Writer.writeEvents()`는 이제 `msEnums` 객체 하나를 받아 그 안의 값만
쓴다. 결과적으로 `engine/*.js`는 MuseScore API를 전혀 import하지 않는
순수 데이터/로직 모듈이 됐다(오히려 기술설계서 8절의 "엔진은 API를
몰라야 한다" 원칙에 더 맞게 됨). **재테스트 필요**: 뮤트/액센트가 이제
정상적으로 보이는지 확인해달라.

## 8-2단계: 기본 코드/패턴 라이브러리 대폭 확충

사용자 요청으로 "기본으로 쓸 수 있는" 코드 운지·리듬 패턴을 대량으로
채워 넣었다.

### 코드 운지 (`data/voicings/user_voicings.json`)

12개 근음(C~B) × 메이저 / 마이너 / 도미넌트7(7) / 마이너7(m7) / sus4 /
dim7, 총 **72개 코드 이름에 127개 운지**를 자동 생성했다.

- 오픈 포지션이 자연스럽게 나오는 조합(E, A 계열)은 "오픈"으로,
  나머지는 E폼/A폼 이동식 바레코드("바레(E폼)", "바레(A폼)")로 생성했다.
  즉 12개 키 전부에 대해 오픈 코드 + 하이코드(바레) 운지를 같이 제공한다.
- dim7은 대칭 구조라는 성질을 이용해 5번줄(A현) 루트 하나의 이동식
  모양만으로 12키를 전부 커버했다(`X-3-4-2-4-X` = Cdim7 형태를 기준으로
  검증).
- `data/voicings/open_chords.json`(기본 제공, C/G/Am/F/Dm/G7/Em/D/E/A)에
  이미 있는 자연스러운 오픈 코드와 겹치는 운지는 중복 생성하지 않고,
  그 대신 바레(하이코드) 버전만 대체 운지로 추가했다. 두 파일은
  `VoicingEngine.mergeLibraries()`에서 합쳐지므로, 예를 들어 C 코드는
  오픈(기본) + 바레(E폼) + 바레(A폼) 3가지 중 골라 쓸 수 있다.

**알고 있는 한계**: 이 자동 생성은 E폼/A폼 두 가지 이동식 모양만 쓴다.
D/G/C가 원래 갖고 있는 고유한 "D폼/G폼/C폼" 오픈 코드(예: Dsus4의
`xx0233` 같은 모양)는 이 자동 생성 범위 밖이라 포함되지 않았다
(대신 E폼/A폼 기반의 등가 코드가 들어 있다). 필요하면 Voicing Editor로
직접 추가하면 된다.

### 리듬 패턴 (`data/patterns/`)

기본 제공 패턴을 3개 → **12개**로 늘렸다.

| 카테고리 | 패턴 |
| --- | --- |
| 고고 | GoGo Basic, GoGo 8Beat, GoGo Mute, GoGo Fast |
| 컨트리 | Country Basic, Country Boom-Chick, Country Eighth Train |
| 칼립소 | Calypso Basic |
| 발라드 | Ballad Basic |
| 슬로우락 | Slow Rock 8Beat |
| 포크 | Folk Eighth |
| 셔플 | Shuffle (Straight Approx.) |

**알고 있는 한계**: 셔플의 스윙(3연음 느낌)은 현재 엔진이 지원하지 않아
스트레이트 8분음표로 근사했다(패턴 파일의 `description`에 명시). 왈츠(3/4)는
엔진이 마디 길이를 4/4로 고정 가정하고 있어서 잘못된 결과가 나올 걸 알면서
넣느니 아예 뺐다(9단계 이후 박자표 지원 확장 시 추가 예정).

## 8-4단계: 기본 제공 패턴 대량 확충 (13개 카테고리, 37개 패턴)

기본 제공 리듬 패턴을 12개 → **37개**로 늘렸다. 3/4박자나 셋잇단음표(스윙,
셔플의 진짜 스윙, 왈츠 등)는 엔진이 지원하지 않으므로 요청대로 전부
빼고, 4/4에 8분음표/16분음표 단위로 표현 가능한 패턴만 넣었다.

| 카테고리 | 개수 | 비고 |
| --- | --- | --- |
| 고고 | 4 | Basic / 8Beat / Mute / Fast |
| 슬로우고고 | 3 | Basic / Boom-Chick / Mute |
| 셔플 | 3 | 전부 "Straight Approx." — 스윙 대신 스트레이트 8분음표로 근사 |
| 칼립소 | 3 | Basic / Syncopated / Mute |
| 보사노바 | 3 | 트레실로(3-3-2) 강세 위치(1·2.5·4)를 기준으로 한 근사 |
| 컨트리 | 3 | Basic / Boom-Chick / Eighth Train |
| 폴카 | 3 | Basic / Oom-Pah-Pah / Fast |
| 트로트 | 3 | Basic / Fill(16분음표 필인) / Fast |
| 룸바 | 3 | Box / Muted / Busy |
| 비긴 | 3 | Basic / Muted / Busy |
| 발라드 | 2 | Basic / Pulse |
| 슬로우락 | 2 | 8Beat / Chug |
| 포크 | 2 | Eighth / Busy |

**알고 있는 한계**: 보사노바·룸바·비긴은 전통적으로 클라베/트레실로 같은
당김음 구조를 쓰는데, 엔진이 표현할 수 있는 건 베이스/코드/뮤트/쉼표와
8분·16분음표 길이뿐이라(셋잇단음표·타이 불가) 세 장르 모두 "1·2.5·4박
강세" 골격을 공유하는 근사치로 만들었다. 실제로는 뮤트 강도, 타이,
당김음의 미묘한 차이로 장르가 갈리는데 그 부분까지는 이번 엔진 구조로
커버되지 않는다(패턴 JSON의 `description` 필드에 근사치라는 점을 밝혀뒀다).

## 8-3단계: 패턴 선택 2단계화 + 미리보기 캔버스

메인 생성기의 패턴 콤보박스가 "[카테고리] 이름" 한 줄짜리 단일
콤보박스였는데, 이걸 Pattern Editor(6단계)와 똑같은 방식 —
**카테고리 콤보 → 그 안의 패턴 콤보** 2단계로 바꿨다. 그리고 패턴을
고르면 그 자리에서 바로 리듬 그림이 그려지는 미리보기 Canvas를
추가했다(위 칸=코드, 아래 칸=베이스, X=뮤트, 주황색=액센트 — Pattern
Editor의 표기 규칙과 동일하게 맞췄다).

- `categoryCombo` : 패턴 카테고리(고고/컨트리/칼립소/발라드/… + 사용자
  패턴의 카테고리) 선택
- `patternCombo` : 선택된 카테고리 안의 패턴만 골라서 보여줌
- `patternPreviewCanvas` : 현재 로드된 패턴(`loadedPattern`)을 매 박자
  단위로 그려주는 순수 미리보기(수정 불가, Pattern Editor의 편집용
  그리드와는 다름)

카테고리/패턴을 고르면 바로 미리보기가 갱신되므로, 어떤 리듬인지
악보에 쓰기 전에 눈으로 먼저 확인할 수 있다.

## 다음 할 일 (실제 MuseScore 4.7에서 직접 해야 하는 것)

이 환경에는 MuseScore 실행 파일이 없어 QML 플러그인을 직접 실행/검증할 수 없다.

1. `ErayChord/` 폴더 전체를 MuseScore Plugins 폴더에 복사
2. `Plugins > ErayChord`(메인 생성기)를 실행해 위 "8단계에서 가장 먼저
   확인할 것" 5가지를 순서대로 확인
3. 필요하면 `Plugins > ErayChord > Pattern Editor` / `Voicing Editor`로
   패턴·운지를 추가한 뒤, 메인 생성기에서 "라이브러리 새로고침" →
   새로 만든 것이 콤보박스에 뜨는지 확인
4. 결과(특히 import 오류 여부)를 알려주면 그에 맞춰 다음 작업(문제 있으면
   단일 파일로 되돌리기, 없으면 9단계로 — 다른 박자표 지원, 진짜 아르페지오
   지원 등 "알고 하는 한계" 해소)을 진행하겠다.
